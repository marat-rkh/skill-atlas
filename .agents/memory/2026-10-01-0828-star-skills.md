## What happened

1. Issue #5 asked to "start skills" in the web interface, with "starred skills shown first". We read "start" as "star".
   The user asked for the work with no further discussion, so the design choices below were made without them and are
   explained in the PR.
2. **Spec:** a "Stars" section under the web interface. Each skill has a ☆/★ button, and clicking it reloads the page
   with the same filter and grouping. Without grouping, starred skills lead the list; with grouping, they form a
   "Starred" group before all others. The other groups are formed from all skills, as with the filter. A star belongs
   to a skill directory in a repository, with owner and name compared ignoring case. The CLI ignores stars.
3. **Code:** `stars.go` (`starStore`, the file `skill-atlas/stars.json` in `os.UserConfigDir()`), `POST /star` in
   `web.go`, which redirects (303) back to `/scan`, and `skillMap.groups(grouping, starred)` in `atlas.go`. The CLI passes
   `nil`. The handler is wrapped in `http.CrossOriginProtection`. Tests were added to every test file. 21 deliberate
   bugs, introduced one at a time, each made tests fail.
4. **Checked in a real browser** against `vercel-labs/agent-skills` and `openai/skills`, then recorded the web part of
   the demo with the new stars scenes. The CLI part was not re-recorded: VHS is not available, and the CLI is unchanged.

## Decisions

- **Stars are kept on the server in a file, not in `localStorage`.** All the ordering stays in Go and is covered by
  `go test` in CI, and the page still needs no JavaScript. The cost is that a click scans the repository again, as the
  filter does.
- **Stars are keyed by skill path, not by name,** because openai/skills has two `openai-docs` skills. Repository keys
  are lowercased because GitHub ignores case.
- **`serve` listens first and then reads the stars file,** so a busy port is still the first error reported. An invalid
  file stops `serve` and names the path. Each change is written through a temporary file and a rename, under a mutex,
  and is kept in memory only if it was saved.
- **Demo media goes to the orphan branch `demo-assets`,** one folder per PR. The repo is private, and `gh` cannot
  upload PR attachments, so this lets the PR description show the screenshots and link the clip without adding binaries
  to `main`. `record.sh` now gives the server its own `HOME`, so recordings start without stars.

## Findings

- **The cloud environment has no Chrome, no sudo, no gcc,** so `go test -race` cannot run. `cdn.playwright.dev`,
  `storage.googleapis.com` and `files.pythonhosted.org` are blocked. npm and `archive.ubuntu.com` work. What worked for
  Playwright:
  - **Browser:** `npm pack @sparticuz/chromium` (Chromium 153, the version Playwright 1.63 expects). Brotli-decompress
    `bin/*.br` with node's zlib, and launch with `executablePath` and `LD_LIBRARY_PATH` set to the bundled
    `al2023/lib`.
  - **Fonts:** `fonts-dejavu-core` and `fonts-dejavu-mono` from the archive pool, unpacked with `dpkg-deb -x`. Point
    `FONTCONFIG_FILE` at a config that lists their directory.
  - **ffmpeg:** `npm pack @ffmpeg-installer/linux-x64` (static, with libx264 and libvpx). Copy it to
    `~/.cache/ms-playwright/ffmpeg-1011/ffmpeg-linux`, and Playwright's `recordVideo` works.
  - **Recording:** run a copy of `web.mjs` with `channel: 'chrome'` replaced by these launch options.
- **`pkill -f <pattern>` kills the shell running it** when the pattern also appears in the same command line.
- **`gh pr checks` fails** with "Resource not accessible by integration". Use `gh run list` and `gh run watch` instead.

## Left open

- Every star click scans the repository again, as every page load does (there is still no caching). After a click, the
  page is shown from the top.
- The CLI could show stars too; the spec says it ignores them for now.
- Whether to keep `demo-assets` as the convention for PR demos is up to the user.
